# 后台管理模块设计

## 功能模块

后台管理模块划分为：

### 应用管理

- 应用列表。
- 新增、查看、修改和删除应用。
- 进入目标应用的版本管理页面。

### 版本管理

- 查看、搜索、筛选和分页展示版本。
- 发布 APK 或 WGT。
- 查看和修改版本记录。
- 上线、下线、单条删除和批量删除版本。

### 安装包管理

- 上传 APK/WGT。
- 手动填写并测试下载地址。
- 删除本次上传文件。

### 更新执行

- APK 和 WGT 统一强制更新。
- 通过上线和下线控制客户端可取得的版本。

## 1. 应用管理

### 1.1 应用列表

应用列表展示已录入的应用，并提供新增、详情、修改、删除和版本管理入口。

应用数据使用 `upgrade-app`，字段包括：

- `id`：记录主键。
- `appid`：应用 AppID，也是版本归属标识。
- `packageName`：Android APK 包名。
- `name`：应用名称。
- `description`：应用说明。

### 1.2 新增应用

新增应用时填写：

- `appid`，必填且唯一。
- `packageName`，必填。
- `name`，必填。
- `description`，选填。

保存成功后，应用进入应用列表，并可发布 APK 和 WGT 版本。

### 1.3 查看和修改应用

应用详情展示全部基本信息，并允许修改：

- `packageName`。
- `name`。
- `description`。

`appid` 作为应用与版本的关联标识，创建后不可修改。

### 1.4 删除应用

删除应用前进行确认。确认后删除当前应用，以及所有 `appid` 等于该应用 AppID 的版本记录。版本关联的对象存储文件是否同时删除，按后续对象存储设计执行。

### 1.5 进入版本管理

从应用列表进入目标应用的版本管理页面，以该应用的 `appid` 加载版本列表。页面顶部显示当前应用和“创建”按钮；当前页面只管理进入时指定的应用，不提供应用切换功能。

## 2. 版本列表

### 2.1 列表字段

版本列表展示：

- 更新标题。
- 更新内容。
- 包类型：APK 或 WGT。
- 版本号和创建时间。
- WGT 最低原生版本。
- 下载地址。
- 上线状态：已上线或未上线。
- 操作入口。

列表数据来自 `upgrade-app-versions`，字段包括：

- `id`。
- `appid`。
- `title`。
- `contents`。
- `type`。
- `version`。
- `min_uni_version`。
- `url`。
- `stable_publish`。
- `createdTime`。

### 2.2 排序

APK 和 WGT 记录合并展示，并固定按 `createdTime desc` 排列，即后创建的版本记录在前。

### 2.3 搜索、筛选和分页

版本列表支持：

- 按当前应用筛选。
- 按更新标题搜索。
- 按包类型筛选。
- 按上线状态筛选。
- 分页加载、展示总记录数和切换页码。

新增、修改、上线、下线或删除成功后刷新列表。

### 2.4 操作入口

- 所有版本均可通过“修改”打开编辑弹窗。
- 所有版本均支持单条删除。
- 所有版本均支持多选和批量删除。

## 3. 发布新版

### 3.1 选择包类型

在版本列表页顶部点击“创建”后打开统一发布弹窗，在弹窗中选择 APK 整包或 WGT 资源包。表单自动带入当前应用 `appid`，包类型由用户在新建时选择；进入修改状态后，`appid` 和包类型均不可修改。

### 3.2 公共发布字段

APK 和 WGT 共用字段：

- `appid`：当前应用 AppID，只读。
- `title`：更新标题，必填。
- `contents`：更新内容，必填。
- `type`：`apk` 或 `wgt`，新建时在统一发布弹窗中选择。
- `version`：版本号，必填。
- `url`：安装包下载地址，必填。
- `stable_publish`：是否立即上线，默认 `false`。

### 3.3 APK 发布字段和约束

- `type` 固定为 `apk`。
- 不保存 `min_uni_version`。
- 可上传 `.apk` 文件或手动填写 HTTPS/CDN 下载地址。

### 3.4 WGT 发布字段和约束

- `type` 固定为 `wgt`。
- `min_uni_version` 必填，表示安装该 WGT 所需的最低原生 APK 版本。
- 可上传 `.wgt` 文件或手动填写 HTTPS/CDN 下载地址。

### 3.5 版本号校验

版本号对应 Android `versionName`，整体以字符串保存，固定使用 `x.y.z` 格式，分别表示主版本号、次版本号和修改版本号。`x`、`y`、`z` 均为非负整数，例如 `1.0.0`。

后台在新增版本时校验版本号必填、`x.y.z` 格式以及当前应用下版本号不得重复。APK 和 WGT 共用一个交替递增的版本号序列，例如 APK 为 `1.1.0`，后续 WGT 可依次为 `1.1.1`、`1.1.2`。后台不要求新版本必须高于当前已上线版本，也允许版本号高低顺序不连续；版本号创建后不可修改。

版本号大小比较属于更新检查服务的职责。服务端按 `x.y.z` 的整数分段比较版本，并分别判断 APK 和 WGT：APK 与客户端 `apkVersion` 比较，WGT 与客户端 `wgtVersion` 比较且校验 `min_uni_version <= apkVersion`。WGT 兼容时优先返回 WGT；WGT 不兼容且 APK 需要更新时返回 APK；安装或重启后再次检查其余更新。

### 3.6 文件上传

发布表单支持两种包地址录入方式：

1. 上传 APK/WGT 文件，上传成功后自动回填下载地址。
2. 直接填写已有 HTTPS/CDN 下载地址。

上传要求：

- 一次只上传一个文件。
- APK 只接受 `.apk` 文件。
- WGT 只接受 `.wgt` 文件。
- 显示已选文件和文件大小。

### 3.7 保存版本

提交发布表单时校验字段和版本号格式。

- `stable_publish=false`：创建未上线版本，客户端更新检查不使用该版本。
- `stable_publish=true`：创建已上线版本；如果同一 `appid + type` 已有已上线版本，先将原版本设为未上线。

保存成功后刷新版本列表。同一 `appid + type` 最多有一个已上线版本，也可以没有已上线版本。

## 4. 版本编辑

### 4.1 编辑入口

点击版本列表中目标记录的“修改”，直接打开编辑弹窗。弹窗展示：

- AppID。
- 包类型。
- 更新标题。
- 更新内容。
- 版本号。
- WGT 最低原生版本。
- 下载地址或包文件。
- 上线状态。

`appid`、包类型和版本号以禁用状态展示，其余允许字段可以直接编辑。

### 4.2 可编辑字段

可编辑字段包括：

- 更新标题。
- 更新内容。
- WGT 最低原生版本。
- 下载地址或包文件。
- 上线状态：未上线版本可以设为上线，已上线版本可以设为下线。

以下字段只展示，不可编辑：

- AppID。
- 包类型。
- 版本号。

### 4.3 提交

- 提交时校验可编辑字段，按 `id` 更新版本记录；可以仅提交变化字段，也可以提交完整的可编辑字段。
- 上线时自动处理同一 `appid + type` 的原已上线版本；下线时不自动上线其他版本。
- 更新成功后关闭弹窗并刷新版本列表。

本设计不增加差异审计、修改历史或数据库差异记录。

### 4.4 已上线版本

已上线版本可以修改更新标题、更新内容、WGT 最低原生版本和下载地址，也可以下线或删除。

## 5. 版本上线与下线

上线状态在版本编辑弹窗中修改。

### 5.1 上线

1. 将未上线版本的上线状态改为上线并提交。
2. 校验版本信息，不比较当前版本与原已上线版本的大小。
3. 如果同一 `appid + type` 已有已上线版本，将原版本设为未上线。
4. 将当前版本设为上线并刷新数据。

上线版本可以低于或等于原已上线版本。该操作只改变服务端当前分发的版本，不会使已经安装更高版本的客户端自动降级；更新检查服务仍按客户端上报版本判断是否返回更新。

### 5.2 下线

1. 将已上线版本的上线状态改为未上线并提交。
2. 将当前版本设为未上线并刷新数据。
3. 不自动上线其他版本。

没有已上线版本时，客户端无法取得该包类型的更新。

## 6. 删除

### 6.1 删除版本

单条删除：

1. 在版本列表中点击目标记录的“删除”。
2. 显示确认提示。
3. 确认后按 `id` 删除版本记录。
4. 刷新版本列表。

批量删除：

1. 在版本列表中勾选一个或多个版本并点击“批量删除”。
2. 显示确认提示。
3. 确认后删除所选版本记录并刷新列表。

已上线和未上线版本均可删除。删除已上线版本后不自动上线其他版本。

### 6.2 删除应用

1. 从应用列表选择应用并点击“删除”。
2. 显示确认提示。
3. 确认后删除应用及其全部 APK/WGT 版本记录。
4. 刷新应用列表。

版本关联的对象存储文件是否同时删除，按后续对象存储设计执行。

## 7. 更新执行规则

APK 和 WGT 统一执行强制更新流程。客户端收到有效更新后进入不可取消的更新流程。

## 8. 数据与业务约束

### 8.1 应用约束

- `appid` 必填且唯一，创建后不可修改。
- `packageName` 必填。
- `name` 必填。
- 版本记录必须关联已存在的应用。

### 8.2 版本约束

- `appid` 必填。
- `title` 必填。
- `contents` 必填。
- `type` 只能是 `apk` 或 `wgt`。
- `version` 对应 Android `versionName`，必填并以字符串保存；格式固定为 `x.y.z`，三个分段均为非负整数，且当前应用下不得重复，创建后不可修改。
- `url` 必填。
- `stable_publish` 默认 `false`。
- WGT 的 `min_uni_version` 必填。
- APK 不保存 `min_uni_version`。
- 同一应用的 APK 和 WGT 共用版本号序列，`version` 不得重复；不同记录的版本号允许高低顺序不连续。
- 同一 `appid + type` 最多有一个已上线版本，允许暂时没有已上线版本。

### 8.3 操作约束

- 未上线版本可以编辑、上线或删除。
- 已上线版本可以编辑、下线或删除。
- 上线时自动下线同一 `appid + type` 的原已上线版本。
- 下线或删除已上线版本时，不自动上线其他版本。
- 上线替换、应用级联删除和批量删除由服务端校验。
- 前端校验用于即时提示，服务端执行同等业务校验。

## 9. 后台管理接口清单

本节定义重实现后台管理模块所需的最小可用产品（MVP）接口。后台管理接口统一使用 `/api/v1/upgrade` 业务前缀。用户身份和后台管理权限通过认证信息判断，不写入资源路径。客户端更新检查使用独立公开路径 `/rest/upgradeCheck`，见第 10 节。

列表接口中的 `page` 从 `1` 开始，`pageSize` 表示每页记录数。以下响应示例统一使用 `code`、`message` 和 `data`，其中仅 `code=200` 表示请求成功，其他 `code` 均表示失败；分页数据使用 `list`、`total`、`page` 和 `pageSize`。

| 方法 | 接口 | 对应功能 | 入参 | 响应示例 |
|---|---|---|---|---|
| `GET` | `/api/v1/upgrade/apps` | 应用列表、搜索、分页 | Query：`keyword`（选填，搜索 AppID、应用名称、包名或应用说明）、`page`、`pageSize` | `{"code":200,"message":"success","data":{"list":[{"id":1,"appid":"com.example.demo","packageName":"com.example.demo","name":"示例应用","description":"Android 示例应用"}],"total":1,"page":1,"pageSize":20}}` |
| `POST` | `/api/v1/upgrade/apps` | 新增应用 | Body：`appid`、`packageName`、`name` 必填；`description` 选填 | `{"code":200,"message":"success","data":{"id":1,"appid":"com.example.demo","packageName":"com.example.demo","name":"示例应用","description":"Android 示例应用"}}` |
| `GET` | `/api/v1/upgrade/apps/{appid}` | 查看应用详情 | Path：`appid` | `{"code":200,"message":"success","data":{"id":1,"appid":"com.example.demo","packageName":"com.example.demo","name":"示例应用","description":"Android 示例应用"}}` |
| `PUT` | `/api/v1/upgrade/apps/{appid}` | 修改应用 | Path：`appid`；Body：`packageName`、`name`、`description`；`appid` 不可修改 | `{"code":200,"message":"success","data":{"id":1,"appid":"com.example.demo","packageName":"com.example.demo","name":"示例应用新版","description":"修改后的说明"}}` |
| `DELETE` | `/api/v1/upgrade/apps/{appid}` | 删除应用及其全部关联版本 | Path：`appid` | `{"code":200,"message":"success","data":{"appid":"com.example.demo","deletedAppCount":1,"deletedVersionCount":6}}` |
| `GET` | `/api/v1/upgrade/versions` | 查询指定应用的版本列表，支持搜索、筛选和分页 | Query：`appid` 必填；`keyword`（更新标题，选填）、`type`（`apk`/`wgt`，选填）、`stable_publish`（`true`/`false`，选填）、`page`、`pageSize` | `{"code":200,"message":"success","data":{"list":[{"id":1,"appid":"com.example.demo","title":"版本 1.2.0","contents":"修复已知问题","type":"apk","version":"1.2.0","url":"https://cdn.example.com/demo-1.2.0.apk","stable_publish":true,"createdTime":"2026-09-24T10:00:00Z"}],"total":1,"page":1,"pageSize":20}}` |
| `POST` | `/api/v1/upgrade/versions` | 新建 APK/WGT 版本，可创建为上线或未上线；创建为上线时由服务端原子下线同一 `appid + type` 的原已上线版本 | Body：`appid`、`title`、`contents`、`type`、`version`、`url` 必填；`stable_publish` 选填且默认 `false`；WGT 的 `min_uni_version` 必填，APK 不传 | `{"code":200,"message":"success","data":{"id":1,"appid":"com.example.demo","title":"版本 1.2.0","contents":"修复已知问题","type":"apk","version":"1.2.0","url":"https://cdn.example.com/demo-1.2.0.apk","stable_publish":true,"createdTime":"2026-09-24T10:00:00Z"}}` |
| `GET` | `/api/v1/upgrade/versions/{id}` | 取得目标版本记录，供编辑弹窗初始化；根据版本 `appid` 解析只读应用名称 | Path：版本记录 `id` | `{"code":200,"message":"success","data":{"id":2,"appid":"com.example.demo","appName":"示例应用","title":"资源包 1.2.1","contents":"更新页面资源","type":"wgt","version":"1.2.1","min_uni_version":"1.2.0","url":"https://cdn.example.com/demo-1.2.1.wgt","stable_publish":false,"createdTime":"2026-09-24T10:01:00Z"}}` |
| `PUT` | `/api/v1/upgrade/versions/{id}` | 修改版本可编辑字段及上线状态；上线时由服务端原子下线同一 `appid + type` 的原已上线版本 | Path：版本记录 `id`；Body：`title`、`contents`、`url`、`stable_publish`，WGT 可传 `min_uni_version`；不接收 `appid`、`type`、`version` 的修改 | `{"code":200,"message":"success","data":{"id":2,"appid":"com.example.demo","appName":"示例应用","title":"资源包 1.2.1","contents":"更新页面资源和样式","type":"wgt","version":"1.2.1","min_uni_version":"1.2.0","url":"https://cdn.example.com/demo-1.2.1.wgt","stable_publish":true,"createdTime":"2026-09-24T10:01:00Z"}}` |
| `DELETE` | `/api/v1/upgrade/versions/{id}` | 单条删除版本，包括已上线版本；删除后不自动上线其他版本 | Path：版本记录 `id` | `{"code":200,"message":"success","data":{"id":1,"deletedCount":1}}` |
| `DELETE` | `/api/v1/upgrade/versions` | 按版本记录 ID 集合批量删除，包括已上线版本；删除后不自动上线其他版本 | Body：`ids`，非空整数数组 | `{"code":200,"message":"success","data":{"requestedCount":3,"deletedCount":3}}` |
| `POST` | `/api/v1/upgrade/files` | 上传单个 APK/WGT 文件并返回可回填至版本表单的文件信息和下载地址 | `multipart/form-data`：`file` 必填；`type` 必填，取值为 `apk` 或 `wgt`，并与文件扩展名一致 | `{"code":200,"message":"success","data":{"fileName":"demo-1.2.0.apk","size":52428800,"type":"apk","url":"https://cdn.example.com/demo-1.2.0.apk"}}` |

### 9.1 接口职责约束

- 版本管理页由应用列表携带 `appid` 进入，不提供应用切换或单独的应用选项接口。
- 新建版本接口负责校验 `version` 必填、`x.y.z` 字符串格式及当前应用下版本号不得重复，但不要求高于当前已上线版本；修改版本接口不接收 `version`。
- 创建已上线版本或将历史版本设为上线时，服务端在一次操作中下线同一 `appid + type` 的原已上线版本，并保证最终最多只有一个已上线版本。
- 将已上线版本改为未上线时，只下线当前版本，不自动选择其他历史版本上线。
- 删除应用及其关联版本由服务端一次完成，前端不组合调用应用删除和版本删除接口。
- 单条和批量删除均允许删除已上线版本；删除后不自动选择其他历史版本上线。
- 文件上传接口只负责保存文件并返回文件信息或下载地址；版本记录由 `POST /api/v1/upgrade/versions` 或 `PUT /api/v1/upgrade/versions/{id}` 保存。
- 手动填写 HTTPS/CDN 下载地址不需要单独接口，由版本新增或修改接口直接接收 `url`。
- 下载地址测试由后台页面直接发起网络请求，不增加业务查询接口。

## 10. 更新检查服务

更新检查服务面向客户端启动检查，公开路径为 `/rest/upgradeCheck`，不属于后台管理页面的增删改查接口。服务端负责校验客户端版本、读取已上线版本、完成 APK/WGT 选择，并且每次最多返回一个更新包。

### 10.1 更新检查接口

```text
POST /rest/upgradeCheck
Content-Type: application/json
```

请求体：

```json
{
  "appid": "com.example.demo",
  "apkVersion": "1.2.0",
  "wgtVersion": "1.2.1"
}
```

| 字段 | 类型 | 必填 | 说明 |
|---|---|---:|---|
| `appid` | string | 是 | 当前应用 AppID |
| `apkVersion` | string | 是 | 当前 APK 版本 |
| `wgtVersion` | string | 是 | 当前 WGT 版本 |

`apkVersion` 和 `wgtVersion` 均须符合固定 `x.y.z` 格式，三个分段均为非负整数。

请求成功但没有更新时返回：

```json
{
  "code": 200,
  "message": "success",
  "data": {
    "action": "none"
  }
}
```

请求参数或数据异常时返回：

```json
{
  "code": 200,
  "message": "success",
  "data": {
    "action": "error",
    "message": "appid、apkVersion、wgtVersion不得为空"
  }
}
```

需要更新时返回一个包。APK 响应示例：

```json
{
  "code": 200,
  "message": "success",
  "data": {
    "action": "update",
    "package": {
      "id": 1,
      "appid": "com.example.demo",
      "title": "版本 1.3.0",
      "contents": "修复已知问题",
      "type": "apk",
      "version": "1.3.0",
      "url": "https://cdn.example.com/demo-1.3.0.apk"
    }
  }
}
```

WGT 响应示例：

```json
{
  "code": 200,
  "message": "success",
  "data": {
    "action": "update",
    "package": {
      "id": 2,
      "appid": "com.example.demo",
      "title": "资源更新 1.2.2",
      "contents": "更新页面资源",
      "type": "wgt",
      "version": "1.2.2",
      "min_uni_version": "1.2.0",
      "url": "https://cdn.example.com/demo-1.2.2.wgt"
    }
  }
}
```

更新包字段：

| 字段 | 必填 | 说明 |
|---|---:|---|
| `id` | 是 | 对应 `upgrade-app-versions.id` |
| `appid` | 是 | 对应 `upgrade-app-versions.appid` |
| `title` | 是 | 更新标题 |
| `contents` | 是 | 更新内容 |
| `type` | 是 | `apk` 或 `wgt` |
| `version` | 是 | 目标版本号 |
| `min_uni_version` | WGT 必填 | 安装 WGT 所需的最低 APK 版本 |
| `url` | 是 | APK/WGT 下载地址 |

响应统一使用 `code`、`message` 和 `data`。正常到达更新检查逻辑后外层通常返回 `code=200`、`message=success`，客户端主要依据 `data.action` 处理：`none` 表示无更新，`update` 表示返回一个待更新包，`error` 表示请求参数、数据状态或处理结果异常。网络请求失败、无法取得有效响应或外层 `code!=200` 同样按检查失败处理。

### 10.2 服务端处理逻辑

服务端按以下顺序处理一次更新检查：

1. 初始化响应为 `code=200`、`message=success`、`data.action=none`。
2. 请求体为空时，在 `data.message` 中返回“请求参数不得为空”；该分支保持初始化后的 `action=none`。
3. 校验 `appid`、`apkVersion` 和 `wgtVersion` 必填；不满足时返回 `action=error` 和对应消息。
4. 校验 `apkVersion` 和 `wgtVersion` 符合固定 `x.y.z` 格式；不满足时返回 `action=error` 和对应消息。
5. 根据 `appid` 查询 `upgrade-app`；应用不存在时返回 `action=error`。
6. 分别查询该 `appid` 下 `type=apk`、`stable_publish=true` 和 `type=wgt`、`stable_publish=true` 的版本记录。
7. 任一包类型查询到多条已上线记录时返回 `action=error`，不从冲突记录中自行选择。
8. 如果线上 WGT 存在，并且 `wgt.version > wgtVersion` 且 `wgt.min_uni_version <= apkVersion`，立即返回 `action=update` 和该 WGT。
9. WGT 未被返回时，如果线上 APK 列表为空，当前处理返回 `action=error` 和“apkList为空”。
10. 线上 APK 存在且 `apk.version > apkVersion` 时，返回 `action=update` 和该 APK。
11. 线上 APK 不高于客户端 APK 时，返回初始化的 `action=none`。

版本比较按 `x.y.z` 的三个整数分段依次比较，不按普通字符串排序。APK 只与客户端 `apkVersion` 比较；WGT 只与客户端 `wgtVersion` 比较，并使用客户端 `apkVersion` 判断最低原生版本兼容性。

### 10.3 选择结果约束

- 满足升级条件且兼容当前 APK 的 WGT 优先于 APK 返回。
- 需要升级但不兼容当前 APK 的 WGT 不返回；此时 APK 需要升级则返回 APK。
- WGT 不兼容且 APK 不需要升级时返回 `action=none`。
- APK 和 WGT 分别与对应的客户端版本比较，不在两个包之间直接比较版本号。
- 一次请求最多返回一个包，不同时返回 APK 和 WGT。
- 客户端安装或重启后重新采集实际 APK/WGT 版本并再次检查，服务端可在后续请求中返回另一个包。
- 只有 `stable_publish=true` 的版本参与更新检查；历史未上线版本不参与选择。
- 服务端返回已选包的存储字段，不要求客户端再次进行版本比较或 WGT 兼容性选择。
- 同一应用的 APK 和 WGT 共用且不得重复的版本号序列；该发布约束不改变检查时 APK 与 WGT 分别和各自客户端版本比较的规则。

### 10.4 异常处理

当前服务逻辑以下列结果表达检查异常：

- 请求体为空：保持 `data.action=none`，并在 `data.message` 返回错误原因。
- 请求字段缺失。
- `apkVersion` 或 `wgtVersion` 格式错误。
- `appid` 对应的应用不存在。
- 同一 `appid + type` 存在多条 `stable_publish=true` 记录。
- WGT 未返回且线上 APK 列表为空。

除请求体为空分支外，上述业务异常返回 `code=200`、`message=success`、`data.action=error`，具体原因放在 `data.message`。网络请求失败、服务未返回有效协议结构或外层 `code!=200` 作为传输或系统异常处理。

客户端收到 `action=error` 时不得将其当作 `none` 放行。`none` 表示检查成功且无需更新，应用可以继续启动；`error` 表示未能可靠完成检查。由于本项目执行强制更新检查，客户端应展示 `data.message`，缺失时显示统一错误文案，并停留在不可关闭的检查页面，仅提供重新检查。请求体为空分支虽然保持 `action=none`，客户端在发起请求前仍必须保证请求体及三个字段齐全，避免将该服务端分支误判为无更新。
